# vllm-rwkv: RWKV-7 served by vLLM, side by side with Qwen on the 3090 (2026-09-25)

The owner pointed at `https://github.com/rwkv-rs/vllm-rwkv` for running a Jev on the GPU beside the Qwen vLLM server. Read
statically in the sandbox at the pinned commit below; nothing was run in the sandbox.

## What it is

- A fork of vLLM (branch `rwkv-torch`, pinned at 67f0c5996c50dca0ad779da545cb491527de988f, committed 2026-08-04, Apache-2.0) that adds
  `RWKV7ForCausalLM` (`vllm/model_executor/models/rwkv7.py`, registered in `vllm/model_executor/models/registry.py:205`) with its own
  CUDA kernels (`csrc/libtorch_stable/rwkv7/*.cu`, built as the `vllm.rwkv7_ops` extension, `setup.py:1259`).
- **RWKV-7 allocates no vLLM KV cache blocks.** Its per-request recurrent state is owned by a model state (`vllm/v1/worker/gpu/
  model_states/rwkv.py`), so its GPU memory is mostly the weights (about 0.8 GB for 0.4B in fp16) plus small states.
- **It has a recurrent-state prefix cache** in that file (`get_longest_prefix`, snapshots cloned on a hit). That is the stream-state
  server the JEV-FIT plan needs: send the session stream once as a prefix, then ask many short questions from the cached state.

## Why it fits "side by side"

vLLM serves one model per process. Side by side means two vLLM processes on the one 3090: the Qwen server with a smaller memory
share, and the RWKV server beside it. Because RWKV holds no KV cache, the Qwen server gives up only a little memory. The cost is
Qwen KV tokens, which is lane capacity (222,822 tokens today, two long-context lanes), and it must be measured.

## Limits (the fork's `docs/models/supported_models.md`, the note under the RWKV7 row)

- Raw BlinkDL `.pth` checkpoints from `BlinkDL/rwkv7-g1` only, with the `rwkv_vocab_v20230424` tokenizer. FLA or Hugging Face
  checkpoints are not supported, so our pinned `RWKV/RWKV7-Goose-World2.9-0.4B-HF` cannot be served as is: the test needs a G1
  `.pth`, and the student we train must end in that format (train with BlinkDL's trainer, or convert).
- CUDA only (no CPU inference); no LoRA, `torch.compile`, normal KV prefix caching, speculative decoding or piecewise CUDA graphs.
- The V1 engine with Model Runner V2 (`VLLM_USE_V2_MODEL_RUNNER`).
- The fork's CI runs only on RTX PRO 6000 machines (`.github/workflows/rwkv7-pro6000-chain.yml`); the 3090 (sm_86) is untested by them.
- A workflow rebases the branch on upstream vLLM (`.github/workflows/rebase-rwkv.yml`), so old commits can vanish from it: the pin
  is by commit, and the build keeps its source.

## The side-by-side test (a GPU test window, D-088)

1. No lane live; stop `qwen.service` (the runbook and `scripts/gpu_window.sh`).
2. The RWKV server alone: load time, memory, latency on the P1 replay's captured Jev requests, and the speed of questions asked from
   a cached prefix state.
3. The Qwen image started with a smaller `--gpu-memory-utilization` beside the RWKV server: both serving; measure the Qwen KV tokens
   left (lane capacity) and the RWKV latency under Qwen load.
4. Restore `qwen.service`; check `/v1/models`.

A permanent split of the card (Qwen's memory share cut for good) goes to the owner with these numbers (D-088).

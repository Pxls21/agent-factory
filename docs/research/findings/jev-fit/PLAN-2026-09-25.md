# JEV-FIT: Jev pipelines for our workflow (the integration plan, version 2, 2026-09-25)

**Status: a design, not a build. Version 2, rewritten at the owner's direction (D-087, 04:5xZ).** Version 1 (same path, in git
history) judged each decision point as a lone Jev question against a simple rule, split "our workflow" from "the product", and
missed the Jev tool the owner had already installed. The owner's correction: our Claude Code workflow is the agent factory's test
bed, and Jevs should be composed into pipelines that rank, collect and present what the expensive model reads. The three area
audits in this directory (`area-A.md`, `area-B.md`, `area-C.md`) stay as the measurement record.

## 1. The answer in plain words

- **Our workflow is the test bed.** Everything is built and proven in this Claude Code session, its skills, hooks, pipeline and PC
  lanes, then copied into the factory (D-087). There is no separate "internal or product" decision.
- **The lever is the expensive model's context.** Every call re-sends the whole context (the main session: 17,241 requests at a
  median 460,526 context tokens, audit A). So a Jev pipeline pays twice: it shrinks what enters the context, which makes every
  later call cheaper, and it cuts calls, which saves a whole re-send each.
- **The pattern: RANK, COLLECT, PRESENT.** A Jev scores the pieces (chunks of a tool output, search hits, report findings, files,
  owner rulings). A deterministic step collects them under a budget, always keeps the lines that must stay (errors, totals, paths)
  and archives the rest. A second Jev call chooses how to present what was kept, from fixed forms: full, excerpt plus pointer, a
  one-line count, or "same as the last run". A Jev writes no free text and never decides a gate; if it is slow or down, the text
  passes through unchanged, and the full text is always one pointer away.
- **The start is the tool the owner recommended: the jev-pruner** (`fast-jev-output`, installed 2026-09-22, enabled at user scope,
  its `baseUrl` our local Laya server at 127.0.0.1:47411). It already ranks and collects Bash output. It fired 2 times in this
  session's 19,358 tool results, because its floor (10,000 tokens, about 40,000 characters) skips 98% of our tool-output text.
- **Every pipeline decision is logged with what happened next:** did the model need a dropped chunk, did it read the prefetched
  lines. That log is the metric and the training data at once (D-086).

## 4. Where the Jevs run

- **In the sandbox:** the local Laya server (CPU, 2 threads, loopback 127.0.0.1:47411; `scripts/jev_local.sh`). It reads one block of
  512 to 1,024 tokens, so it suits per-piece questions. It is slow on long requests (28 client disconnects), so P1 sends only
  results of 2k characters or more and batches their chunks in one request.
- **On the PC:** the RWKV stream reader (0.4B; 61,440 tokens read in 1.17 s on the 3090, a question from a copied state in about
  0.046 s, measured with vLLM stopped). A pipeline's rank question needs the session's history (the pruner sends up to 25,000 tokens
  of history per request; Laya reads 1,024), and a stream reader holds all of it in one state. It is the backend the pipelines grow
  into once its speed beside vLLM, or on the PC's CPU, is measured. The bridge adds 0.6 to 1.6 s per round trip, so calls batch per
  tool result.
- **Everywhere:** fail open. A slow, down or unsure Jev passes the text through unchanged.

## 5. The rules stay, inside the pipelines

The audits' rules become the pipelines' cheap first stage and safety layer: always keep errors, totals and paths (P1); the Stop
attribution line, one line on which uncommitted files are a lane's; KV-budget admission for local lanes (task #180); a poll budget
per route; the habits (task-list and tool-load calls ride with real work). The orient fix (AF-AP-204) already landed.

## 6. Build order

1. **P1, the pruner at our scale.** Lower its floor to about 2k characters, extend it to Read, Grep and agent hand-backs, add the
   present step, and log every decision with what happened next. First, measure its keep rate and misses on a replay of this
   session's tool results.
2. **P2 prefetch and P3 digests:** they cut calls, the largest lever.
3. **P5 owner rulings:** the quality fix for today's errors.
4. **P6 PC lanes:** throughput, once the Hermes seam is found.
5. **P4 resume pack and P7 wake filter.**
6. **The RWKV stream server** as the scoring backend for all of them, after its speed is measured.

Each ships fail-open and logs its decisions from its first day. The pruner is a third-party plugin installed outside the repo
(`/root/jev-plugins/jev-pruner`); `scripts/setup.sh` does not install it, so a new container loses it: vendor it (pinned, with a
provenance record) before changing it.

## 7. How the gain is measured

- **Tokens:** the characters kept out of the context, times the calls that followed until the next compaction.
- **Calls:** a prefetched read the session did not have to make; a digest read instead of several report reads.
- **Misses (the quality bar):** the session reads an archive or re-runs a command to see what a pipeline dropped. A miss is also a
  training label.

## 8. Risks

- **A dropped line the model needed:** the archive pointer, the always-keep rules and the miss metric bound it.
- **Latency:** CPU Laya is slow; only larger results go through, in one batched request each.
- **The GPU:** RWKV beside vLLM on the 3090 is unmeasured; vLLM holds about 95% of the card (AF-AP-201).
- **Privacy:** the pipelines read session text; everything stays on our machines (the local server, the PC), scrubbed before it
  leaves the sandbox. The pruner's default endpoint is TypeSafe's hosted API; ours points at the local server.
- **Feedback:** a model trained on our sessions shapes our sessions; the miss metric and the logged decisions keep that visible.

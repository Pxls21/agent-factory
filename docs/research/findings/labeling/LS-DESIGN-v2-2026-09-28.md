## 1. What changed since v1

- **D-103 (the owner, 14:45Z).** The tools are many, each with its strengths, weaknesses and uses. Neither the
  coordinator nor Jev should decide each time which ones to run. Instead: script stacks tied to labels, so that "because
  of the way the labels are, it'll use the scripts, the tools in the correct way each every time", run "based on the
  variables you put in", and "just give you the output".
- **The premortem: REDESIGN the request transport.** Three failure classes belong to the Stop-hook channel itself, not
  to v1's text (PM gate recommendation):
  - it can drop a request without a word: it reads only the last content block of the final message (PM P3a), it
    misses a thinking-only final message (P3b), and it never runs on an interrupt or an API error (P3d);
  - the binary fixes the continuation semantics: `stop_hook_active` stays true for the rest of a user turn (P1), and
    the harness's own block counter resets at every tool round, which no hook can see (P2);
  - a request round is one more model request, the same cost as a tool call (P27), so the saving must come from what
    each request does, not from the channel.

## 2. The design in one paragraph

A **stack** is a named, fixed sequence of instrument calls with typed parameters, kept in a committed registry
(`scripts/stacks.toml`). The coordinator or a lane runs a stack with ONE tool call:
`python3 scripts/stack.py <label> key=value …`. The runner checks the parameters, runs each step as an argument vector
(never a shell) under its own timeout and output cap, in parallel where the registry groups steps, feeds one step's
output lines to a later step where the registry says so, and prints one combined, sectioned output. It saves each
step's full output under the main tree's `.jev/stacks/<run id>/` and appends one record per run to
`.jev/stacks/runs.jsonl`. The stack call is itself the label: which instruments, with which parameters, on which tree.
The saved outputs are the state a later Jev ranker or pruner would see, stored verbatim (PM P17). Ratings ride on the
next call (`--rate <run id>=<rel>/<use>`): they are stored in the tool input and cannot be lost to a thinking block
(PM P3b; the S1-RATE F1 gap).

## 3. Transport: a tool call now; the chat form only on the owner's word

- **T1, built first: the Bash tool call.** It is visible in the transcript, waits by construction, passes the
  permission system and the auto-mode classifier, works in subagents and in PC lanes (a Hermes lane's terminal tool runs
  the same command), has no continuation cap, and cannot drop a request silently.
- **T2, the chat form (`REQ <nonce> <id> <label> key=value`, run by a Stop hook): NOT built now.** It can lose a
  request without a word in cases no specification closes (PM P3a, P3b, P3d), and it saves nothing over T1 (PM P27).
  The owner's literal words in D-101 (3) ("write it in the chat ... end, wait") pick T2; their stated reasons (fewer
  calls, fewer tokens, the right tools every time, labels for every Jev use) are all met by T1. The coordinator
  recommends T1 and asks the owner. If the owner still wants T2, it becomes a thin front end over the same runner, and
  PM's transport list A is its brief.

## 4. The registry and the runner

### 4.1 The registry

TOML (`tomllib` is in the standard library: Python 3.11.15 here, 3.12 on CI). One table per stack: a `summary`, the
hand sequence it `replaces`, typed `params` (`path`, `paths`, `symbol`, `text`, `word`, `agent`, `choice`), and
ordered `steps`. A step has an `id`, an `argv` with placeholders, a `timeout`, a `cap_lines`, the exit codes that count
as success (`ok_rc`), `required`, an optional parallel `group`, an optional `when` (parameter equals value) and an
optional `repeat`. `stack.py list` prints the catalog, one line per stack; `stack.py explain <label> key=value …`
prints the exact plan and runs nothing. The full schema is in the LS-B9 brief.

### 4.2 The rules the runner enforces

- **No shell, ever.** A placeholder fills whole argument elements (a list splices as separate elements); a `text`
  value that begins with `-` is refused (option injection); shell metacharacters are inert.
- **Paths.** A `path` value resolves inside the target tree and is refused when it hits the deny list (`.pc-bridge.env`,
  any `*.env`, `.git/`, `/root/.codiv/`, `/root/.claude/projects/`, `~/.config/qwen-*`,
  `/root/.config/session-export/`) before any step runs.
- **Trees.** The target tree is the git toplevel of the current directory, named in the output header. The log and the
  saved outputs live in the MAIN tree's `.jev/stacks/`, found through `git rev-parse --git-common-dir`, so worktrees
  share one log (AF-AP-235's class: state that follows the wrong tree).
- **Fail loud.** A missing instrument prints `unmapped — <tool> unavailable` for its step (the wording of
  `lane_context.sh`); a step over its timeout is killed with its whole process group and reported
  `TIMEOUT after N s`; a required step that fails makes the run exit 1. Nothing degrades silently.
- **Output.** A header (stack, run id, tree, HEAD), then one section per step headed by the exact command, shell-quoted,
  with its exit code and time; each section capped at `cap_lines`, naming the saved full output; the whole print capped
  at 9,000 characters.
- **Exit codes.** 0: every required step passed. 1: a required step failed. 2: a usage or parameter refusal. 3: a
  registry or log error.
- **Wave 1 has no model call and no outward action.** Every stack is deterministic and reproducible from the tree
  (KC-J1: no Laya or Jev in a gate). A later Jev part ranks or prunes a stack's sections from the ratings; it never
  chooses the stack (D-103: "not jev, decide").

## 5. Labels and ratings

- **The record.** One line per run in `runs.jsonl`: run id, UTC time, label, parameters, tree, HEAD, and per step the
  argv, exit code, time, output size and sha256, and the saved path. That is the D4 label "which instruments, on what"
  with its answer, the stack's output, stored whole.
- **Ratings.** `--rate <run id>[.<step>]=<rel>/<use>` on any later call, or `stack.py rate …`, appends a rating record
  for that run. Content stacks only (`find`, `ctx`, `impact`, `echo`): a rating of a gate count means nothing (PM P20).
  S1-RATE stays as it is, and comes first in a message.
- **What Jev learns from it later.** Which sections of a stack's output the coordinator used (the ratings, and the
  next edits), so a pruner can cut what is never used. The pruner's input is the saved output itself, so the state it
  learns from is exactly the state it will see (PM P17).

## 7. Measures (pre-registered before LS-B9 lands)

- **Baseline.** From the main transcript of 2026-09-20 to 09-28, for each wave-1 stack, the hand calls in the sequence
  it replaces, per occurrence (for example, the calls between a lane's completion notice and its harvest ledger line).
- **After one week of use.** The same count, plus the stack calls; model requests per harvest and per gate.
- **Kill criterion.** A stack that does not cut the hand calls of its sequence, or whose output misled an action (a
  wrong or stale answer the coordinator acted on), is fixed or dropped.
- **X-010's pilot (PM P27, P36).** Per task (the span of one ledger id): model requests, cache-read plus output tokens,
  and wall time, against the same baseline; the threshold and the kill criterion are set before the pilot starts.

## 8. What v2 does not do

- No chat-form requests (T2) until the owner asks for them.
- No model call inside a stack, and no stack chosen by a model.
- No outward action from a stack (push, comment, publish, PC server control).
- No change to the vendored output-style files.

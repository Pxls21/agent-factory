## 3. The design in one paragraph

The coordinator writes three kinds of typed lines. A **label** records a decision it makes (the actor's own choice,
AUDIT class D4), at the moment it makes it, with the context in view. A **request** asks Jev or a script to do
something; requests go in the FINAL message of a turn, and a Stop hook runs them and returns the results before the
coordinator continues. A **rating** scores each result on the S1-RATE scale. Everything a harness field already records
(exit codes, errors, gate lines) is logged by a hook with no model effort. A collector joins labels, requests, results,
ratings and outcomes into per-family records, scrubbed and value-gated, which become each Jev instance's training and
test sets.

## 4. The three typed lines (the grammar)

Each typed line is a short text of its own, at most 200 characters, starting at column 0, outside any code fence or
quote. (A long text written before a tool call can be stored as thinking, not text: VERIFY-S1-RATE F1, AUDIT §2.1.)

1. **Label:** `LBL <family>.<question> <answer> [why: <at most 120 chars>]`
   - `<family>.<question>` comes from a committed registry (`labels/families.json`, LS-B8): for example
     `f12.bake`, `f23.route`, `f26.repair`, `f29.echo_class`, `f31.drift`, `f36.read_next`, `f37.changes_gate`,
     `f38.wake_now`, `f39.dup_of`, `f40.claim_holds`. The registry holds each question's type (choice, score, yes/no)
     and its option set; the collector refuses an unknown family or an answer outside the set.
   - Only D4 decisions get LBL lines. A decision whose answer a harness field records (D1, D2) is never hand-labeled.
2. **Request:** `REQ <nonce> <id> <verb> <args>`
   - `<nonce>` is the current turn's nonce (§5.2). `<id>` is `r1`, `r2`, … within the turn.
   - Verbs, closed set v1: `ask` (a semantic code question: graft first, Jev locate second), `find` (a literal search,
     capped), `read` (a file and a goal: the narrowed window, §7), `book` (bookkeeping: §6), `status` (a lane, a CI run
     or the bridge, read-only).
   - A turn that ends with requests takes no other action in that message.
3. **Rating:** `RATE <id> rel=<0-3> use=<0-3> [note]`, one per result, the S1-RATE scale; `S1-RATE` lines stay as they
   are.

## 5. The request loop

### 5.1 Flow

1. The coordinator ends a turn with one or more REQ lines.
2. The Stop hook `ls-exec` reads `last_assistant_message`, parses the REQ lines, runs each verb under a budget
   (§5.3), and exits 2 with a RES block on stderr (the harness feeds it back as the reason to continue):
   `RES <id> ok|refused|error|timeout <result or reason>`, then the next nonce and one rating request.
3. The coordinator continues: RATE lines first, then its work.

### 5.2 Safety

- **Nonce.** Each RES block (and the UserPromptSubmit hook, for the first request of a turn) prints a fresh random
  nonce. A REQ line with any other nonce is ignored and reported as `ignored: stale nonce`. A quoted report, a pasted
  document or an old message therefore cannot trigger a request.
- **Closed verbs, no shell.** Each verb is a Python function with a schema. Arguments never reach a shell; paths are
  resolved and checked against an allowlist; `book` writes only to the allowlisted files and anchors (§6).
- **No outward action.** No verb pushes, comments, publishes, or touches the PC's servers. `status` is read-only.
- **The continuation cap.** The harness allows 8 consecutive continuations (AUDIT §4.3). `ls-exec` counts them in its
  state file and, at 6, answers `refused: continuation budget` and exits 0, so the harness never hits its own cap.
- **Coexistence.** `stop_hook_active` is read. The retro gate and the git check keep their jobs; `ls-exec` runs first
  and adds nothing when the message has no REQ line.
- **Fail loud.** A verb that fails says so in its RES line; nothing fails silently.

### 5.3 Budgets

- One Stop hook call has a wall budget (60 s default) across all its verbs; a verb over its share answers `timeout`.
- The RES block is capped at 9,500 characters (the harness caps hook text at 10,000); a longer result is written to a
  file under `.jev/ls/results/` and the RES line names it with a preview.

## 6. The offload (`book`) and the task list

- `book ledger <task> <text>`: appends a dated line after the ledger's newest block; the stamp comes from the clock
  (the typed-stamp class, CLAUDE.md, ends by construction).
- `book incident <text>` and `book registry <row>`: the incident log's newest-first entry, and a registry row after the
  last `AF-AP-` row (the id is the next free one, computed).
- `book wiki <text>`: a new live-state block at the top of Active lanes.
- `book decision <row>`: a D-row after the last one (the next free id).
- Each `book` write takes a lock, runs the tests that name the path (a committed map), and reports the count line; it
  never commits. Commits and pushes stay the coordinator's (they carry judgment and outward effect).
- **The task list.** Scripts cannot call the harness's task tools. The ledger is the SSoT already. Proposal for the
  owner: the in-session task list becomes a view: a UserPromptSubmit hook injects the ledger's active tasks (the D-rows'
  open tasks, at most 10 lines), and the coordinator stops mirroring by hand (1,207 calls in eight days). This changes a
  CLAUDE.md rule, so it waits for the owner's word.

## 7. The Read-narrowing hook (task #340, X-011)

- A PreToolUse `Read` hook, ported from BorisLeMeec/jev e81c1d0 (MIT; AUDIT §5.1): 400-line floor; only without an
  explicit offset or limit; one request per file (80 KB cap); the window `max(lines/5, 150)` centred on Jev's line; an
  undo note in `hookSpecificOutput.additionalContext` (the documented place; AUDIT §6 item 6); fail-open on any error.
- The goal: the `read` verb's goal when there is one; otherwise the coordinator's most recent LBL or REQ line; the last
  user message only as a fallback (the owner's messages are long dictations).
- The jev bench shows that confidence does not separate hits from misses on large files; its size gate is what
  protects (AUDIT §5.1). So the port keeps the size gate and adds our own measurement: a labeled set from this repo's
  own Reads (the 301 unranged large-file Reads and the lines the session went on to use), recall measured before the
  hook is on by default.
- Every narrowing is logged as an F42 record (goal digest, file, window, confidence, and whether the session read
  outside the window within 5 calls: the outcome label).

## 8. The free labels and the collector

- **LS-B4, the action log.** A PostToolUse hook (PostToolBatch where it works) appends one record per tool call:
  tool, a digest of the input, the outcome fields (D1, D2), the nearest preceding LBL or REQ id. This streams what
  DATA-SESSION and JEV-MAP derive after the fact today.
- **LS-B3, the collector** (`scripts/ls_collect.py`, generalizing `s1_scores.py`): joins LBL, REQ, RES, RATE and the
  action log into per-family JSONL records (state digest, answer, rating, outcome), scrubbed by `transcript_export`
  and value-gated; per-family counts per day.
- **LS-B8, the family registry** (`labels/families.json`): each family's question, type, options, the Jev instance it
  trains, and its label source (D1 to D5). The registry is the contract between the output style and every consumer.

## 9. What LS does not do

- It never lets a model judge a gate (the no-LLM-judge spine).
- It never labels from outside the decision (the SYNTH1 lesson: two labelers without the context failed).
- It never replaces a harness field with a model label.
- It adds no second model egress for the Agent Factory: in the factory, Hermes tool calls already are typed requests
  that pass the fail-closed `pre_tool_call` gate; LS's factory form is logging each call with its state and outcome.

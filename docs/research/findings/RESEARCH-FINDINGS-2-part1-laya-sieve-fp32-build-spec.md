# Build Specification: A Self-Hosted Advisory "Typed-Decision" Relevance-Sieve Layer on Laya

## TL;DR
- **Build it, but on FP32, not INT8.** Laya, TypeSafe System One, winnow, jev-pruner, and jevcache all exist and are verified from primary sources; the winnow design is the right thing to fork. The single most important finding: on the owner's AMD Ryzen 5 5600X (Zen 3, AVX2, **no** AVX-VNNI/AVX-512), INT8 quantization does **not** speed a ModernBERT-large encoder up — the "Is INT8 Portable?" study (arXiv 2609.16085) states verbatim that cores lacking a dot-product ISA "slow down by 1.7x, for the identical model and runtime." **FP32 is the realistic floor**, so per-block sieving must be asynchronous or PC-only.
- **Projected wins (to be measured, not asserted):** at the measured ~1.0–1.25 s/question FP32 floor, sieving is only viable when many blocks are judged in the background off the critical path. On the coordinator lane (tool output = 46.9% of transcript) and the PC lane (tool output = 90% of context bytes), a keep/drop sieve that hides ~50–70% of judged tool-output bytes yields a first-order input-token reduction of roughly **0.469 × 0.6 ≈ 28% per coordinator transcript** and **0.90 × 0.6 ≈ 54% of PC-lane context bytes** — but only above a byte floor set where ≥80% of bytes live, and only if the added latency (N × ~1 s) is hidden.
- **Ceiling:** a ~395–421M-parameter encoder with a 512-token window fundamentally cannot decide gates, reason over long state, output non-English, or touch the filesystem. It can only rank/flag/classify. The first step beyond it is the `laya-typed-decisions` checkpoint fine-tuned on the project's own labeled pairs (base zero-shot is near chance at 0.362 accuracy; the fine-tuned checkpoint reaches 0.766 on its own benchmark).

## Key Findings

### Project verification (confirmed / corrected / refuted)

**1. Laya — CONFIRMED with important corrections.** GitHub `NandhaKishorM/laya` (Apache-2.0), HF `convaiinnovations/laya`, and PyPI `laya` (0.3.5) all exist. The three checkpoints are real: `laya` (ModernBERT-large, 512-token, English), `laya-multilingual` (mmBERT-base, 322M, 1024-token), `laya-typed-decisions` (ModernBERT-large, 421M on-disk, 1024-token). Note that ModernBERT-large's *architecture* is 395M parameters (28 layers, 1024 hidden; Answer.AI/Hugging Face announcement, Dec 19 2024: "both a base (149M params) and large (395M params) model size"); the **421M figure is Laya's own on-disk checkpoint count** (encoder plus decision/scoring/action heads), so both numbers are correct at different layers of the stack. The API is `laya.load("convaiinnovations/laya", subfolder=...)` and `Router(preload=True).predict(state, questions)`; [GitHub](https://github.com/NandhaKishorM/laya) there is also `Router.route()` for a no-forward-pass routing decision. Question schema is `{"type": "choice"|"score"|"noul", "instructions", "criteria"}`. The state/head split is confirmed from the model card: English defaults to 512 context with `head_max_len=192` (~320 tokens for state); the 1024-token checkpoints use `head_max_len=256` (~768 for state).

**Corrections/challenges:** (a) The README headline of **0.766** for typed-decisions is the *fine-tuned* checkpoint on its own training split; the *base* `laya` checkpoint scores **0.362** accuracy with **ECE 0.175** zero-shot — below the 0.461 majority-class baseline. [github](https://github.com/NandhaKishorM/laya) The card itself admits "all of the capability on this benchmark comes from fine-tuning." [github](https://github.com/NandhaKishorM/laya) (b) FP16 is the default; `dtype="float32"` is for closer numerical agreement, and Laya notes bf16 "can be requested but is not part of the published validation matrix." (c) Community ports confirm the forward path: **each question is a separate encoder forward pass — there is no batch amortization** ("every question still gets its own encoder computation"; the MoonBit port states "No batching. Each question is a separate forward pass"). [GitHub](https://github.com/majikxu/laya.mbt) (d) States longer than the window are right-truncated by the builder budget (community LiteRT port: "A row longer than 512 tokens after the checkpoint's own builder needs a shorter input"). (e) v0.3.5 introduced temperature clamping to [0.5, 5.0] because a shipped `choice:11+` bucket temperature of 0.1006 "would sharpen logits ~10x and report a coin flip as near-certainty." (f) `laya-multilingual` ships no fitted temperatures at all (`temperature: [1, 1, 1]`). **Not verifiable from the accessible sources:** the exact `laya/` package internals (thread-safety, reload behavior) — treat as gates to measure; the upstream README confirms CPU reload is expensive (7.4 s median reload on CPU at `max_loaded=1`, 193–464 ms/request on CPU when preloaded).

Response shape confirmed via LiteLLM's pass-through docs: `answers[qid] = {type, choice, probabilities, confidence}` plus `usage.{input_tokens, output_tokens}`. [LiteLLM](https://docs.litellm.ai/docs/pass_through/typesafe) Three primitives (Choice, Score, Noul) confirmed. Pricing is $0.042/1M input tokens, $0 output. Jev is early-access/waitlisted; `jev-latest` currently resolves to `jev-1.13.0`. [DEV Community](https://dev.to/valyuai/how-to-use-jev-a-practical-guide-to-typesafes-system-one-model-g5e) The documented "skill" design pattern is confirmed from the docs: build a compact state of only what the question needs, ask independent typed questions, combine answers with deterministic code ("Because System One models return typed, constrained outputs rather than free-form text, your code can inspect and combine its answers into predictable workflows"). **3. winnow — CONFIRMED; this is the design to fork.** GitHub `GhalebDweikat/winnow` (MIT). Confirmed: Claude Code plugin using a resident sidecar `winnow serve` on `127.0.0.1:47311`; splits tool output into ~25-line blocks (`WINNOW_BLOCK_LINES=25`, `WINNOW_MAX_BLOCKS=200`, `WINNOW_MAX_STATE_CHARS=120000`); asks one noul per block ("is this block needed for the current task?"); keep ≥`WINNOW_KEEP` (0.5), drop <`WINNOW_DROP` (0.1), keep the uncertain middle; **errors are never hidden** (error-gate); optional Haiku summarizer for hidden groups; `winnow_recall` MCP tool restores dropped blocks by cache key; [github](https://github.com/GhalebDweikat/winnow) shadow mode (`WINNOW_MODE=shadow`) and a keyless `lexical` replay baseline exist. This matters enormously for Q5 (see below). The state shape `{task, tool, blocks}` and the per-block question are confirmed.

**4. jev-pruner — CONFIRMED.** GitHub `tamaratran/jev-pruner` (MIT, TypeScript; [GitHub](https://github.com/tamaratran/jev-pruner) Claude Code identifiers still `fast-jev-output`). Confirmed: a `tool.call` hook that wraps the Bash tool result; a **strict 10,000-estimated-token floor** below which nothing is pruned (`minTokens`, "minimum 10,000; equality skips pruning"; can raise but not lower); a portable core `trimOutput({command, goal, output, messages}, asker, options)`; one noul per chunk; first/last chunks and diagnostic/result lines always kept; a Codex path that is an **opt-in model-invoked wrapper** (`node dist/codex/run.js -- <cmd>`) because "Codex CLI 0.152.1 does not support replacing native shell output from PostToolUse." There is a `SYSTEM_ONE_URL` constant, and the Codex wrapper carries an unused `baseUrl` param — a one-line fix points it at a local endpoint.

**5. jevcache — CONFIRMED as README+binary only (no source).** GitHub `hyperspaceai/jevcache`; issue #3 "There is no source code in this git repo" [GitHub](https://github.com/hyperspaceai/jevcache/issues/3) and issue #2 "No LICENSE file" [GitHub](https://github.com/hyperspaceai/jevcache/issues/2) confirm the task's premise: README-only, no source, no license. It ships a ~2–3 MB binary via `curl -fsSL jevcache.sh/install | sh`. The decision-cache contract is real: `key = sha256(model ⊕ schema ⊕ canonical(redact(state)))`, append-only local ledger, verbs `decide|recall|publish|add|serve|replay`. The local backend contract `JEVCACHE_LOCAL_URL=http://127.0.0.1:8080/v1/decide` with `{state, questions} -> {answers}` is worth honoring. **Security caveats confirmed from issues:** it writes a `state_preview` (first ~200 chars of canonicalized state) in plaintext to a world-readable ledger (issue #1), and it drops `user_id`/`order_id` before hashing so two subjects can collide on one cached decision (issue #2). **Recommendation: adopt the design, decline the dependency** — build a first-party ledger.

### Q3 — Fast CPU inference: the decisive result

The subagent's targeted research resolves Q3 cleanly and **against INT8** on this hardware:
- **Zen 3 (Ryzen 5 5600X) has no int8 dot-product instruction.** A Ryzen 5 5600X CPU-ID dump confirms `AVX/AVX2 [Y/Y] … AVX512-VNNI [N] … AVX512-BF16 [N] AVX-VNNI-VEX [N]`, and TechPowerUp's 5600X architecture review notes "a notable absentee is AVX-512 … You still do get 256-bit instructions from within the AVX2 set." AMD's VNNI arrived with **Zen 4** (first AMD AVX-512, including AVX512-VNNI) and **256-bit AVX-VNNI with Zen 5** (Wikipedia "Zen 5": "AVX-512 instructions have been extended with the VP2INTERSECT extension, in addition to 256-bit AVX-VNNI").
- **The arXiv study "Is INT8 Portable?" (2609.16085) states verbatim: "The sign of the INT8 speedup is set by the CPU's dot-product ISA (ARM dotprod/SDOT, x86 VNNI): cores that have it speed up by up to 2.1x, cores that lack it slow down by 1.7x, for the identical model and runtime."** The 5600X is squarely in the "slow down 1.7×" camp.
- **Corroboration on BERT specifically:** ONNX Runtime issue #6695 measured bert-base on a VNNI-less Ryzen 3700X (Zen 2, analogous) at fp32 38.05 ms vs int8 35.08 ms — ~1.08×, effectively no gain — versus Cascade Lake (VNNI) fp32 31.46 → int8 19.76 (~1.6×). ONNX Runtime's own docs: "x86-64 with VNNI, GPU with Tensor Core int8 support and Arm®-based processors with dot-product instructions can get better performance in general," and non-VNNI machines need reduce-range just to avoid saturation ("Reduce-range will quantize the weights to 7 bits. It is designed for the U8S8 format on AVX2 and AVX512 (non-VNNI) machines to mitigate saturation issues. This is not needed on machines supporting VNNI").
- **OpenVINO** is Intel-tuned; its INT8 fast paths target VNNI/AMX. On AMD/non-x86, "ONNX Runtime is usually equal or better" (Ultralytics). No structural INT8 win on the 5600X.
- **bf16 on Zen 3 is emulated, not hardware** (AVX512-BF16 = N on the 5600X), so bf16 will be slow.
- **Batching does not amortize on CPU** and this is architectural, not a bug: Laya's own runtime and every community port confirm each question is a separate ~512-token encoder pass, and a ~400M-param matmul at seq-512 already saturates the CPU's vector units at batch 1, so a padded batch of N pairs costs ≈ N single passes.
- **ModernBERT CPU gotcha:** its throughput advantage comes from FlashAttention-2 unpadding, which **only activates with `attn_implementation="flash_attention_2"` (CUDA + flash-attn installed)** — the transformers source states that without it "the implementation will use PyTorch's SDPA kernel, which requires padding and unpadding inputs, adding some overhead." On CPU/ONNX/OpenVINO the model falls back to SDPA, and FlashAttention subgraphs do not ONNX-export cleanly (they unfold into many matmuls). At a fixed 512-token padded window this simply means you pay the full dense-attention cost — there is no unpadding win to lose on a single 512-token sequence.

**Q3 decision rule (restated with the verdict):** adopt the fastest export whose answers agree with FP32 within ±0.02 mean-absolute probability on a labeled set AND whose p50 ≤ 300 ms/question on 4 cores. **On the 5600X and the 4-core sandbox, no export is expected to clear this bar** — INT8 will regress (~1.7×), bf16 is emulated. Therefore **FP32 stays, and per-block sieving must be asynchronous (fire-and-forget, judged in the background) or PC-only (batched offline over a lane's report inputs), never inline on the coordinator's critical path.** This is a gate to confirm by measurement, but the published evidence makes FP32 the planning assumption. The only reliable INT8 benefit here is ~4× smaller model size / lower memory bandwidth, not latency.

### Q5 — Claude Code Bash rewrite seam: the seam does NOT fire for Bash on affected builds
Primary sources give a clear, cautionary answer:
- **`PostToolUse` `updatedToolOutput`** shipped in v2.1.121 (2026-04-28) and is documented to work "for all built-in tools: Bash, Read, Write, Edit, Glob, Grep, WebFetch, and MCP tools."
- **But issue #68951 documents a regression**: `updatedToolOutput` is **silently ignored for the built-in Bash tool** on 2.1.163 and 2.1.177 — the hook runs, reports success, but the model still receives the original output. "Any PostToolUse output transform for built-in tools is inert." No fix version is named in the issue (marked stale); **whether 2.1.278 fixes it is unverified and must be tested**.
- **Function hooks** (`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`, present in the binary since 2.1.260) can *resolve a tool call with a result* — the 2.1.260 binary carries a `tool.call … resolved by a hooks module (result)` branch on which "the tool never runs" — but this is a preview behind a flag that "has not shipped," documented only in the binary, with no stability guarantee.
- **`PreToolUse` `updatedInput`** reliably rewrites the *command* (documented, stable) — this is the seam that always works and is the basis for the `sieve-run` wrapper.

**Q5 verdict:** Do **not** assume `updatedToolOutput` fires for Bash on 2.1.278. Ship the deterministic fire-test (below); if it fails, the **`PreToolUse` MODIFY that rewrites the command into `sieve-run -- <cmd>`** (a wrapper that runs the command and returns pruned stdout while preserving exit code/stderr/timing) is the only reliable sandbox integration — mirroring exactly what jev-pruner had to do for Codex.

### Q4 — Hermes harness seam: CONFIRMED and clean
From the primary Hermes docs (nousresearch.com) and the v0.21 follow-ups issue:
- `pre_tool_call` is **directive/control**: returns `{"action": "block"|"approve"|"modify", ...}`. **`modify` returns are shallow-merged into the tool arguments** ("The returned `args` dictionary is shallow-merged over the original tool arguments before the tool executes"). It also accepts the Claude-Code-compatible `{"decision": "modify", "tool_input": {...}}`.
- `post_tool_call` is an **observer** whose return is ignored — confirmed.
- **Better than a command rewrite:** Hermes ships a purpose-built **`transform_terminal_output`** transform hook — "First `str` replaces the output" for the `terminal` tool, running before secret redaction — and a general **`transform_tool_result`** ("The first `str` replaces the result … Applies to every tool"). These are the ideal, low-risk seam: the sieve can rewrite terminal/tool output directly without wrapping the command at all.
- **Critical latency constraint:** `pre_tool_call` and other bounded hooks are governed by `plugins.hook_callback_timeout` (default 30s, max 600) and **`pre_tool_call` fails *closed*** (blocks the tool) on timeout. `transform_*` hooks accept the first valid string replacement and are abandoned (not fail-closed) on timeout. Because Laya on CPU costs ~1 s/question and a large log is many questions, a synchronous transform hook on the PC lane can blow the timeout — **the PC-lane sieve must be bounded (cap questions, hard inner deadline) and fail-open by returning the original output.**

**Q4 verdict:** integrate via **`transform_terminal_output`** (narrowest, purpose-built) with a bounded question budget and a hard wall-clock deadline; fall back to `transform_tool_result` for non-terminal tools. The `pre_tool_call`→`sieve-run` command-rewrite is a viable alternative but riskier (fails closed on timeout, and interacts badly with pipelines/`${PIPESTATUS}`/heredocs/backgrounded commands — see Caveats). The pinned commit `527da60844d4dced37879ea50259675371abe10e` (MIT) could not be fetched directly; the seam contract above is taken from the current hermes-agent hooks documentation and should be re-confirmed against that commit's `model_tools.py`/`handle_function_call()`.

### Q1 — State/question design under a 512/1024 window
- Chunk large output into ~25-line blocks (winnow's default), splitting lines >2,000 chars first (jev-pruner's rule). Build `state = {task:{user_request, assistant_intent}, tool:{name, input}, blocks:{b001:...}}` and ask one noul per block. Keep `task summary + tool + one block + question` inside the 512-token English budget (~320 tokens for state after the 192-token head): a 25-line block at ~8 tokens/line ≈ 200 tokens fits; verify with the tokenizer.
- **Judge a block alone by default.** Neighbor-id context roughly doubles state length and risks truncation; only add neighbor ids when a block is a continuation (e.g., a stack trace split across blocks).
- **The 1024-token checkpoints (`laya-multilingual`, `laya-typed-decisions`) buy a longer block window but cost accuracy** (base zero-shot 0.342/0.362) [github](https://github.com/NandhaKishorM/laya) and, for multilingual, ship no calibration. For English logs/code, stay on the 512-token `laya` checkpoint and chunk smaller rather than moving to 1024.
- **Canonicalize state for a stable digest:** sorted keys, normalized whitespace/Unicode (NFC), redact secret classes *before* hashing. This mirrors jevcache's `canonical(redact(state))` — but avoid its mistakes: do **not** store a plaintext state_preview, and do **not** drop identifying fields that change the decision.

### Q2 & Q9 — Calibration + labeled-set sizing
- **Method:** per-question-type temperature scaling is the right default (single scalar T on logits; cheap; Laya already fits one temperature per (question type, option count), moving mean ECE 0.466→0.081 for `laya` and 0.314→0.106 for multilingual). Platt scaling (logistic) and isotonic regression are alternatives; isotonic is more flexible but overfits on small sets and needs more data. For a noul (binary), Platt/temperature suffice; reserve isotonic for when you have thousands of labels.
- **ECE/Brier:** ECE = Σ (|B_m|/N)·|acc(B_m) − conf(B_m)| over M bins; Brier = mean squared error of predicted probability vs outcome (a proper scoring rule; ECE is not — "ECE can be minimized by an uninformative model that always predicts the base rate"). **Report both, plus MCE (worst bin).**
- **Estimator bias & sizing:** ECE is biased (under any binning scheme it underestimates true CE), binning-sensitive, and sample-size-sensitive. Use **equal-frequency (quantile) bins, B = 10–15** ("Most modern calibration audits use equal-frequency bins with B = 10–15"), and **≥ 20–50 samples per bin** → practically **≥ 200–750 labeled examples per question type** for a trustworthy ECE. Prefer a monotonic-sweep (ECEsweep) or SmoothECE estimator to reduce bin-boundary bias — Roelofs et al. show ECEbin selects the right recalibration method only 3/10 times vs 7/10 for ECEsweep.
- **Split discipline:** split by task/lane, **never by block**, to avoid leakage (blocks from one tool output are highly correlated).
- **Sieve metrics:** needle retention (share of later-cited lines a drop would have removed), regret (a dropped block later recalled — winnow's `winnow stats` reports this directly), byte reduction, added latency. Run **shadow mode first** (winnow's `WINNOW_MODE=shadow`), then A/B.
- **Weak-label recipe (winnow's, adopt it):** a block is "needed" if later assistant text or a tool input reuses one of its lines in an edit/write/command, or mentions a distinctive identifier appearing in few other blocks. Treat weak-label regret as an upper bound; [github](https://github.com/GhalebDweikat/winnow) draw a blind stratified sample and hand-label ~100 blocks for a trustworthy number.

## Details

### Build spec — `laya-decide` (loopback HTTP service)
Build order, each with a deterministic acceptance test:
1. **Model host.** Load `laya.load("convaiinnovations/laya", subfolder=..., dtype="float32")`; force FP32 on CPU. Pin the HF revision (e.g. `c5d78730f3493e4fe16d61507ef4b78eef7318cf`, or the current pinned SHA) and record checkpoint SHA + `laya` version + export id. *Test:* load succeeds, `predict` on a fixture returns the documented answer within ±1e-3 of a recorded golden (the LiteRT port validates FP32 parity to 3e-5).
2. **Warm-start + single-worker queue.** One resident process per checkpoint (avoid the 7.4 s CPU reload). A bounded FIFO queue; one in-flight forward pass at a time (CPU saturates at batch 1). Per-request hard deadline. *Test:* 100 sequential calls, zero reloads, zero active-memory growth (community ports confirm zero measured active-memory growth over 100 repeated finite calls).
3. **Two endpoints.** Serve both `/v1/systemone` (TypeSafe-shaped `{model, state, questions} -> {model, answers, usage}`) and `/v1/decide` (jevcache-shaped `{state, questions} -> {answers}`). *Test:* golden request/response for each shape byte-matches the documented schema.
4. **Canonical state builder + redaction.** Sorted keys, NFC, whitespace-normalized; redact `sk-...`, private-key env values, bridge tokens, `.env` contents **before** the digest. *Test:* a state with an injected secret produces a digest identical to the same state with the secret removed, and the secret never appears in the ledger.
5. **Ledger (Q6).** Append-only JSONL; digest input = canonical(redact(state)) + question + checkpoint SHA + export id. Canonical JSON rules: sorted keys, fixed float formatting (or store logits as integers/strings to dodge float non-determinism), NFC unicode. Replay = same digest+checkpoint+export returns the recorded typed answer with no forward pass (the model is deterministic in FP32 for fixed input, so this is bitwise-replayable). Retention/rotation sized for ~40,000 tool results/day (rotate daily, compress). *Test:* replay a recorded day and diff bitwise — zero differences.
6. **Two-venue deployment + no-outbound proof.** User-level systemd unit on loopback (Q10). *Test:* `ss -tanp`/`strace -f -e trace=connect` shows no non-loopback sockets; a network-namespace test with egress blocked still serves.

### Build spec — `sieve-run` (CLI wrapper)
`sieve-run [--floor N] [--mode shadow|summarize|drop] -- <cmd>`:
1. Run `<cmd>` capturing stdout/stderr separately, preserving exit code and timing. Return stderr and exit code untouched.
2. If stdout is below `--floor` (default 10,000 estimated tokens, jev-pruner's floor), pass through byte-for-byte. *Test:* a short command's output is returned identically (byte-for-byte no-op test).
3. Chunk stdout into ~25-line blocks; build canonical state; POST to `laya-decide`; keep ≥0.5, drop <0.1 (note: re-derive thresholds on this project's labels — winnow's 0.1 and jev-pruner's hardcoded 0.1 are their numbers, not yours).
4. Errors never hidden (error-gate noul); gate-script outputs and `sieve-run`'s own commands exempt (exempt-command list). *Test:* an output containing an error line is never pruned.
5. Recall path: dropped blocks cached by key; a `sieve-recall <key>` restores them. Fail-open marker: on judge failure/timeout, emit the original with a `[sieve: fail-open]` marker. *Test:* kill the judge mid-run; output passes through with the marker.

### Q5/Q4 fire-tests
- **Claude Code (Q5):** in a scratch session on 2.1.278 with a `PostToolUse` hook returning `{"hookSpecificOutput":{"hookEventName":"PostToolUse","updatedToolOutput":"SENTINEL"}}` for a Bash `echo hello`. **Fire = model sees `SENTINEL`; no-fire = model sees `hello`.** If no-fire, adopt the explicit `sieve-run -- <cmd>` CLI wrapper (called by hand or via `PreToolUse` `updatedInput` command rewrite).
- **Hermes (Q4):** register a `transform_terminal_output` returning a sentinel for a fixed command. **Fire = terminal output replaced by sentinel.** Confirm the bounded deadline: a hook that sleeps past `plugins.hook_callback_timeout` must fail-open (return original), which requires the sieve to enforce its own inner deadline since `transform_*` is abandoned (not fail-closed) on timeout.

### Q7 / Q8 / Q10 / Q11
- **Q7 (decisions file):** one reviewed file per skill holding the typed-decision constants, invoked by `decide ask <file> <state.json>`. Candidate decisions (all advisory): per-finding severity H/M/L + kind (choice), per-hit role def/caller/config/test/other (choice), a six-dimension advisory bug rating (six scores), relevance re-rank of a lexical top-10 to top-3 (score per row).
- **Q8 (ranked view):** a bounded ranked VIEW beside raw code-search output, capped size, one `score` question per row, budget ~1 s/row — which on FP32 means this must be **PC-only/offline**, not inline on the coordinator path.
- **Q10 (systemd):** user-level unit `laya-decide` on loopback, CPU, ~3 GB RAM per resident checkpoint (peak RSS ~1.44 GB for the large checkpoint per the MoonBit port, plus tokenizer/runtime headroom), health check, log rotation, fail-open on restart.
- **Q11 (per-tool policy):** whole-file reads → a symbol/range-aware judge or an instruction to read by range; terminal output → per-block relevance sieve; byte/token floor set per venue where ≥80% of bytes are above it; gate-script outputs exempt.

## Recommendations
1. **Stage 0 (build the service, FP32).** Ship `laya-decide` on FP32 with the ledger and both endpoints. Do not spend effort on INT8/OpenVINO for this CPU — the evidence says it regresses. Benchmark FP32 p50/question on 4 and 6 cores; confirm the ~1.0–1.25 s floor. **Threshold to change course:** if a future move to Zen 4/Zen 5 (AVX-VNNI) or a second GPU lands, re-run the INT8/FP16 comparison — the up-to-2.1× INT8 win becomes available only with VNNI hardware.
2. **Stage 1 (fire-tests before integration).** Run the Q5 and Q4 fire-tests. Adopt only the seam proven to fire. Expect to use `PreToolUse`/`sieve-run` on Claude Code and `transform_terminal_output` on Hermes.
3. **Stage 2 (shadow mode).** Run in shadow for a week on both lanes; collect `decisions.jsonl`, compute regret vs threshold and byte reduction on real distributions. **Threshold to go active:** regret ≤ 2% at the chosen drop threshold on hand labels, and ≥80% of bytes above the floor.
4. **Stage 3 (calibrate then A/B).** Fit per-question-type temperature on ≥200–750 labels/type; verify ECE with equal-frequency B=10–15 (and an ECEsweep cross-check); then A/B active vs shadow. **Threshold to keep it on:** needle retention ≥ 98% and measured net token reduction that survives the added latency (i.e., background/PC-only, not inline).
5. **Stage 4 (specialize).** If accuracy is the bottleneck, fine-tune `laya-typed-decisions` on the project's own labeled pairs (the upstream notebook runs on 2×T4 in ~4–5 h for 4 epochs over ~30k questions). Expected gain: from ~0.36 zero-shot toward the ~0.77 the fine-tuned checkpoint reaches on its own benchmark.

## Caveats
- **FP32 latency is the binding constraint.** At ~1 s/question and N questions per large log, inline synchronous sieving is infeasible on the coordinator's critical path and marginal on the PC lane; the whole design hinges on judging in the background/offline. This is the biggest risk and must be measured first.
- **The headline numbers are projections, not measurements.** The 28%/54% reductions are first-order (byte-share × assumed prune-fraction); the real numbers come from shadow mode on the owner's own stores. Do not assert them as achieved.
- **Command-rewrite wrapping breaks on pipelines, `${PIPESTATUS}`, `cd` chains, heredocs, interactive/backgrounded commands, and the 420 s timeout cap.** jev-pruner's Codex wrapper explicitly requires `-- bash -c '...'` for shell constructs and buffers stdout to completion (switching to passthrough above 8 MiB). Prefer output-transform seams (`transform_terminal_output`, `updatedToolOutput`) over command rewrites where they fire; where they don't, restrict `sieve-run` to simple non-interactive commands and pass everything else through.
- **The model is advisory only.** It never decides a gate/merge/lint/commit verdict; it ranks, filters, classifies, and flags. Keep it structurally impossible for a sieve decision to change a verdict.
- **Calibration must be re-fit locally.** `laya-multilingual` ships uncalibrated (`temperature: [1,1,1]`); even `laya` is over-confident as shipped; thresholds from winnow (0.1/0.5) and jev-pruner (hardcoded 0.1) are theirs, not yours.
- **jevcache is unverifiable as software** (no source, no license) — honor only its endpoint contract in a first-party build; never pipe its installer.
- **English-only ceiling.** The `laya` checkpoint collapses on non-Latin scripts while staying confident (Khmer 0.000 accuracy at 0.952 confidence), so confidence-gating cannot catch it — never route non-English through it; use the multilingual checkpoint or don't sieve.

## NOT-RESOLVED — empirical gates (each a runnable command + decision rule)
1. **FP32 p50/question on 4 cores.** `OMP_NUM_THREADS=4 python bench.py --n 200` (also set ORT/torch intra-op threads = 4, pin with `taskset -c 0-3`, warm-start first). *Rule:* if p50 > 300 ms (expected ~1 s), inline sieving is off; go async/PC-only.
2. **Does `updatedToolOutput` fire for Bash on 2.1.278?** Sentinel `PostToolUse` hook + `echo hello`. *Rule:* if the model sees `hello`, use `sieve-run`/`PreToolUse`.
3. **Does `transform_terminal_output` fire and respect an inner deadline on hermes-agent 0.21.0 (commit 527da60)?** Sentinel hook + sleep-past-timeout test. *Rule:* if abandoned on timeout, enforce inner deadline + fail-open by returning original.
4. **Byte floor where ≥80% of bytes live, per venue.** Histogram tool-output sizes from `decisions.jsonl`. *Rule:* set `--floor` at that percentile per lane.
5. **Regret vs drop threshold on ~100 hand labels.** `sieve replay sample|label|score`. *Rule:* pick the lowest drop threshold with regret ≤ 2%.
6. **ECE per question type on ≥200–750 labels, equal-frequency B=10–15.** *Rule:* if ECE > 0.05 after temperature fit, widen labels or switch to isotonic.
7. **Bitwise ledger replay of one day.** *Rule:* any diff = the export is non-deterministic; do not enable replay-skip.
8. **No-outbound-socket proof.** `strace -f -e trace=connect` under an egress-blocked netns. *Rule:* any non-loopback connect = fail the deploy.
9. **INT8 vs FP32 on this exact CPU (sanity, expected to fail the bar).** `quantize_dynamic` + ORT bench, 4 threads. *Rule:* adopt INT8 only if p50 improves AND probability drift ≤ 0.02; on Zen 3 expect a regression, so this stays a documented negative result until VNNI hardware exists.
